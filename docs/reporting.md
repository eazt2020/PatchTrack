# Reporting specification

## 1. Report types

| Type | Key | Intended audience | Period |
|------|-----|-------------------|--------|
| Monthly management report | `monthly_management` | Management, service owners | Calendar month |
| Quarterly compliance report | `quarterly_compliance` | Risk, audit, regulators | Calendar quarter |
| Inventory register | `inventory_register` | Platform teams | Any period |

All three render from the same `compliance.snapshots` row. That is what
guarantees the PDF agrees with the dashboard and the API for that period.

## 2. File properties

- Format: PDF 1.4, A4, generated by ReportLab (no headless browser).
- Filename on disk: `<report-id>.pdf`; the download name is
  `patchtrack-<type>-<YYYY-MM>.pdf`.
- Dimensions: A4 with 18 mm margins, dark header band, footer rule with
  classification, organisation and page number.
- Classification marking: `CONFIDENTIAL — INTERNAL USE ONLY` in the footer of
  every page. Change it in
  `services/reporting/app/service.py::build_context`.
- File mode `0640`; the directory is on a dedicated volume.

## 3. Structure

1. **Header** — organisation, period label, generation time, generated-by.
2. **KPI table** — total servers, compliant, non-compliant, unknown, stale,
   excluded.
3. **Executive summary** — the percentage against target, the composition of
   the population, the change versus the previous period, and an explicit
   "Target not met" / "Target met" statement.
4. **Compliance overview** — one table per dimension: operating system,
   environment, business group, application group. Each row shows total,
   compliant, non-compliant, unknown, stale and the group percentage.
5. **Remediation overview** — severity distribution chart, total and critical
   finding counts, and the 15 servers with the most outstanding patches.
6. **Historical analysis** — monthly trend of compliance percentage against
   the target, from immutable daily snapshots. If fewer than two points exist,
   the report says so instead of drawing a line.
7. **Data quality and operational health** — last inventory sync, last patch
   sync, per-integration status and last result.
8. **Methodology** — reporting period, population, numerator, denominator,
   unknown treatment, freshness threshold, blocking severities, policy name,
   and the source systems.

The methodology section is not optional. A report without it cannot be
defended, so it cannot be disabled by configuration.

## 4. Numbers in the report

Every figure is read from the snapshot, never recomputed:

| Report field | Source |
|--------------|--------|
| Population counts | `snapshots.total_servers`, `compliant_servers`, … |
| Percentage | `snapshots.compliance_pct` |
| Target | `snapshots.target_pct` |
| Group rows | `compliance.snapshot_groups` |
| Finding counts | `snapshots.critical_findings`, `total_findings` |
| Policy | `snapshots.methodology` |

Empty population ⇒ the report renders with "n/a" for the percentage. It does
not print 0% or 100%.

## 5. Integrity

1. The PDF is rendered in memory.
2. `validate_pdf` checks the magic bytes (`%PDF-`), a plausible size
   (≥ 1024 bytes) and the trailing `%%EOF` marker.
3. The bytes are written to `<id>.pdf.tmp`, `chmod 0640`, then atomically
   renamed to `<id>.pdf`.
4. The SHA-256 of the bytes is stored in `reporting.reports.sha256` together
   with size and page count.

A report row is `completed` only after all four steps. If any step fails the
row becomes `failed` with the error text, and no file is published.

The digest is what makes "this is the report we issued for October" verifiable:

```bash
sha256sum /var/lib/patchtrack/reports/<report-id>.pdf
psql -c "SELECT sha256, file_size FROM reporting.reports WHERE id='<report-id>'"
```

## 6. Immutability

- A completed report is never overwritten. `generate_report` returns
  immediately if `status = 'completed'`.
- The partial unique index prevents a scheduled period from producing a second
  non-failed report.
- A retry re-renders the **same snapshot**. If the snapshot has since been
  superseded, the retry still renders the original — the report records the
  period as assessed, not the estate as it is now.
- Purged files leave the row intact (filename, digest, size survive), so an
  archived period remains identifiable.

## 7. Scheduling

| Field | Meaning |
|-------|---------|
| `cadence` | `monthly` or `quarterly` |
| `day_of_month` | 1–28 (schema constraint) |
| `run_hour` | 0–23, in the schedule's `timezone` |
| `timezone` | IANA name, e.g. `Australia/Sydney` |
| `recipients` | Array of email addresses |

Run time computation:

- local wall-clock, converted to UTC;
- clamped to the last day of the target month, so a 31st schedule runs on
  28 February and a 26th schedule stays on the 26th;
- monthly advances one month, quarterly three;
- unknown timezone falls back to UTC (logged).

Idempotency: the scheduler inserts a `job_executions` claim on
`(schedule_id, period_start)`. A second instance gets a unique violation and
skips. A failed generation writes `failed` and does **not** consume the
period permanently — the claim row exists, so an operator must retry
explicitly; the report-level unique index permits it because `status='failed'`
is excluded.

The scheduler is driven by `POST /api/reporting/jobs/tick`. Wire it to a
systemd timer or a cron entry calling the gateway with the service token.

## 8. Email delivery

Delivery is independent of generation:

| Outcome | Recorded as | Report status |
|---------|-------------|---------------|
| Sent | `delivery_attempts.status='sent'` | stays `completed` |
| SMTP not configured | `skipped`, "SMTP is not configured" | stays `completed` |
| No recipients | `skipped` | stays `completed` |
| SMTP error | `failed` with the error | **stays `completed`** |

A failed email never invalidates a report. Re-send is a manual operation
(re-request delivery) and the file remains downloadable regardless.

SMTP uses STARTTLS with the default certificate context (`smtp_starttls=true`,
the default). Do not set it to false to work around an internal relay; install
the relay's CA instead.

## 9. Retention

`PATCHTRACK_REPORT_RETENTION_DAYS` (default 2555 = 7 years) governs the file,
not the row. `purge_expired` deletes files past `expires_at` and reports the
count. Archived metadata and the digest remain.

Set the retention to match the organisation's record-keeping obligation. Seven
years is a common default for financial-services environments and is what the
example configuration assumes.

## 10. The dashboard

The Grafana dashboard (`deploy/grafana/dashboards/patchtrack-overview.json`) is
provisioned, not hand-built. Its panels:

| Panel | Content |
|-------|---------|
| Total servers (in scope) | Stat |
| Compliant | Stat |
| Non-compliant | Stat |
| Unknown / stale | Stat |
| Compliance vs target | Stat with threshold |
| Excluded from scope | Stat |
| Compliance by operating system | Stacked bar |
| Compliance by environment | Stacked bar |
| Compliance by business service | Stacked bar |
| Patch status distribution | Donut |
| Monthly compliance trend | Time series with target line |
| Quarterly compliance vs target | Bars with target |
| Outstanding findings by severity | Bar |
| Collection health | Bar |
| Top non-compliant servers | Table |

Template variables: `os_family`, `environment`, `business_group`. The "All"
value is the literal sentinel `__all__`, and each query filters with
`('$var' = '__all__' OR a.col = '$var')`. This avoids Grafana's
`$__conditionalAll` macro, which produced invalid SQL in this dashboard.

The dashboard reads through `patchtrack_grafana` (read-only, 30-second
statement timeout). The application does not depend on it: stopping Grafana
changes nothing except the dashboard being unavailable.
