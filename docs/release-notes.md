# Release notes

## Unreleased — security and integrity corrections

### Guided installer with preflight and automatic rollback

- `install.sh` now performs a guided production installation. It asks for the
  application and configuration paths, service account, bind address, HTTPS
  port, certificate name and first administrator, then installs a missing
  Docker runtime with `dnf` after confirmation.
- Every dependency is checked before the first change: OS and architecture,
  root access, SELinux, CPU, memory, disk, account tools, the container
  runtime, the published port, target directories, an existing Compose project
  and (as warnings) the image/package endpoints.
- Bootstrap credentials are generated by the installer and stored as
  file-backed Compose secrets, not in `.env`. The stack is always started with
  `docker-compose.secrets.yml`.
- The post-install check waits for `/readyz` (all four backends), confirms the
  HTTPS sign-in page, signs in as the first administrator, verifies the session
  and the forced password-change flag. If anything fails, the installer
  reverses its recorded changes in reverse order, including the Compose
  project, image, files, account, service state and package transactions; it
  refuses to touch an existing deployment.
- The installer supports hosts whose only outbound route is an HTTP(S) proxy.
  It asks for the URL (or reads `PATCHTRACK_INSTALL_PROXY`), checks that the
  proxy is reachable, runs `dnf` and the image build through it, configures a
  Docker daemon systemd drop-in for image pulls, and adds `HTTP_PROXY`,
  `HTTPS_PROXY` and `NO_PROXY` to the generated `.env` for the services. The
  proxy URL's credentials are redacted from all output, and rollback removes
  the drop-in and restarts Docker.
- `install.sh --check` runs the same preflight without changing the host.
- `uninstall.sh` reverses an installation from its manifest. It prechecks the
  manifest, paths, runtime, compose project, image, account and configuration
  leftovers; removes the containers, network, image, application tree and only
  the installer-created configuration; keeps an account that pre-dated the
  installation and any operator-created file. Data volumes are preserved unless
  `--purge-data` is given. Post-uninstallation checks verify each removal and
  report preserved volumes and files.
- `upgrade.sh` upgrades an existing deployment from the unpacked new
  release. It preflights the manifest, paths, target version, service account,
  runtime, Compose project, current readiness and free space; takes a mandatory
  backup of the application tree, configuration and a PostgreSQL dump; stages
  and swaps in the new tree; updates `PATCHTRACK_VERSION`; builds the new image;
  stops writes, runs migrations and starts the stack; then verifies `/readyz`,
  `/healthz`, the sign-in page and the migration table. On any failure it
  restores the previous tree, `.env`, manifest and database dump, starts the
  previous version and verifies it. The backup is retained under
  `/var/lib/patchtrack/upgrades`, and downgrades are refused because they need
  a restore rather than an upgrade.

### Secret files for bootstrap credentials

- `PATCHTRACK_DATABASE_URL`, `PATCHTRACK_JWT_SECRET`,
  `PATCHTRACK_SECRETS_KEY`, `PATCHTRACK_SERVICE_TOKEN` and the SMTP password
  fallback may now be supplied by a `*_FILE` sibling variable. The file value
  wins over the plain variable; a missing or unreadable file stops start-up
  rather than falling back, and an empty `_FILE` value means "not configured".
  Files readable by group/others are logged without their content. Existing
  `.env` deployments are unchanged.
- `docker-compose.secrets.yml` is an opt-in override that mounts the database
  URL, JWT secret, service token and PostgreSQL password as Compose secrets and
  masks the plain variables in the container environment. Native deployments
  can use `LoadCredential` / `LoadCredentialEncrypted` with the same
  variables. See [security.md](security.md#secret-files).

### HTTPS from first start

- **The gateway now serves HTTPS itself.** With `PATCHTRACK_TLS_ENABLED=true`
  (the value in `.env.example`, so new installations get it), the first start
  generates a self-signed certificate in `PATCHTRACK_TLS_DIR` (default
  `/var/lib/patchtrack/tls`), so a fresh installation is never exposed over
  plain HTTP. Browsers warn until the organisation's certificate is installed.
- **Administrators can install their own certificate in the UI.** **Settings →
  HTTPS certificate** accepts a PEM certificate (with chain) and unencrypted
  key. The pair is validated before replacing anything, written atomically
  (key mode 0600), loaded into the live listener without a restart, and
  audited as `settings.tls_updated` with public metadata only. `GET/PUT
  /api/tls`; only the `administrator` role may upload, and the session is
  re-confirmed with identity.
- A missing or mismatched half of the pair is refused rather than regenerated,
  and a passphrase-protected key is refused. TLS 1.2 is the floor; HSTS is now
  emitted by the application when a request arrives over HTTPS.
- The gateway and systemd entrypoints use the new
  `python -m patchtrack_common.serve` launcher, which is what applies a
  replaced certificate to the running listener. A gateway started with the
  plain uvicorn CLI still stores the files but requires a restart. An upgraded
  deployment that keeps an external proxy must set
  `PATCHTRACK_TLS_ENABLED=false` in its existing `.env`; unset means the
  previous plain-HTTP behaviour, so upgrades are not switched silently.
- Container and compose changes: the image creates `/var/lib/patchtrack/tls`,
  compose mounts the `tls` volume, and the health check uses HTTPS for the
  gateway. No database migration is required. `starlette` is now an explicit
  image dependency because the gateway imports it directly.

### Email delivery

- **Scheduled reports can now be emailed through an SMTP relay configured in
  the UI.** **Settings → Email delivery** stores host, port, STARTTLS,
  username, password and sender in `shared.app_settings` under `smtp_relay`;
  a saved change applies to the next delivery without a restart. The
  `PATCHTRACK_SMTP_*` environment variables remain the fallback until a relay
  is saved, and the first save carries over an unchanged environment username
  and password.
- The SMTP password is write-only and encrypted at rest with Fernet. The key is
  derived from the new optional `PATCHTRACK_SECRETS_KEY`, falling back to
  `PATCHTRACK_JWT_SECRET`; it is never stored beside the ciphertext. Rotating
  either key makes the saved password unreadable, and delivery reports that
  instead of falling back to unauthenticated mail.
- New endpoints `GET/PUT /settings/smtp` and `POST /settings/smtp/test`
  (`settings:manage`). The test route sends a short message without saving
  anything, and audit events record the host and whether the password changed —
  never the password itself.
- No migration is required: `shared.app_settings` already exists.

### Scheduling

- **Scheduled work now runs inside the services.** Inventory collection,
  the daily compliance snapshot, report schedules and both retention purges are
  executed by an in-app scheduler loop in the owning service. The
  `patchtrack-tick.timer` and `patchtrack-tick.service` units and
  `scripts/patchtrack-tick.sh` are removed; a deployment must remove any
  installed copies (`systemctl disable --now patchtrack-tick.timer`) after
  upgrading, or it will run the old external runner alongside the new loop.
- Due state is stored in `shared.scheduled_jobs` (migration
  `017_scheduled_jobs.sql`), so restarting a service does not replay jobs that
  just ran. A failed job is retried after
  `PATCHTRACK_SCHEDULER_RETRY_SECONDS` (default 300) rather than waiting for
  its full interval.
- A PostgreSQL advisory lock is held for the duration of each job, so two
  replicas cannot execute it at the same time.
- Every job's interval and enabled flag can now be changed at **Reporting →
  Schedules → System jobs** (administrators). The stored value takes effect on
  the next poll without a restart and is recorded as `scheduler.updated`.
  Migration `019_scheduler_ui.sql` adds `enabled` and `updated_by`.
- Cadence is configured with `PATCHTRACK_*_INTERVAL` environment variables
  (see [configuration.md](configuration.md#5-scheduler)). `/etc/patchtrack/tick.env`
  is no longer read. `scripts/patchtrack-job.sh` remains as a manual tool for
  running one job immediately.

### Performance

- The scheduler reads due state for all of a service's jobs in one query per
  poll instead of opening a connection per job.
- Report-file retention is a daily `reporting.retention` job rather than part
  of the 60-second schedule tick, so the report table is no longer scanned
  every minute. The sweep marks all expired files in one statement instead of
  one connection per file.
- Migration `018_performance_indexes.sql` indexes the due-schedule lookup,
  report-expiry sweep, report and sync-run orderings, and snapshot lookup by
  period.

### Session and sign-in

- **Signing out now revokes the access token.** Previously the gateway only
  deleted the browser cookie, so a copied token kept working until it expired.
  Every token carries `identity.users.token_version`; signing out, changing or
  resetting a password, changing a role and deactivating an account increment
  it, and all services refuse a token that carries an old value. Migration
  `016_user_token_version.sql` adds the column. Existing sessions are invalid
  after the upgrade and users sign in once more.
- Administrator password resets and role/deactivation changes also revoke the
  account's refresh tokens, not only its access token.
- Failed sign-ins no longer reveal whether an account exists. Unknown,
  inactive, locked and single-sign-on accounts receive the same **401** body,
  and a dummy password hash is verified for accounts that cannot sign in so
  response timing matches too.
- Failed sign-ins are throttled to 10 per address/account pair and 50 per
  address in 15 minutes, answering **429** with `Retry-After`. Spraying one
  password across many accounts no longer bypasses the per-account lockout.

### Report rendering and export

- Group names, hostnames and branding text are XML-escaped before ReportLab
  parses them, so markup in imported inventory or Settings cannot corrupt or
  inject into a generated PDF.
- CSV exports neutralise cells beginning with `=`, `+`, `-`, `@`, tab or
  carriage return by prefixing an apostrophe, so an imported value cannot
  execute as a spreadsheet formula when an analyst opens the file.

### Request handling

- Request bodies are capped at 64 MiB (`PATCHTRACK_MAX_REQUEST_BYTES`), counted
  as they stream rather than trusted from `Content-Length`. A parser
  `RecursionError` from a deeply nested payload returns **422**.
- `/api/*` paths containing dot segments (including encoded and
  double-encoded forms) are rejected with **400**, closing a route-normalisation
  gap where `auth/../users` could reach a closed identity endpoint.

### Reporting periods

- A quarterly report now covers the **previous calendar quarter**. The old
  calculation produced a two-month window and raised `ValueError` in January.
- The reporting period is a local calendar date. A schedule's time zone
  decides *when* the report runs, never *which* period it selects, so a
  midnight run in Asia/Kuala_Lumpur can no longer look up the previous day and
  miss its snapshot.
- A duplicate claim is still treated as "already running", but a connection,
  permission or timeout failure is now raised instead of silently skipping a
  scheduled report.

### Data integrity

- Satellite and SCCM no longer substitute `datetime.now()` for a missing or
  malformed assessment timestamp. The timestamp is stored as `NULL` ("unknown")
  and the compliance engine evaluates it as unknown, not fresh. Migration
  `013_optional_assessed_at` makes the column nullable; any existing fabricated
  timestamps cannot be distinguished and should be treated as suspect during
  verification.
- An assessment with no timestamp is always re-evaluated rather than deduplicated
  against the previous row.

### Reports

- While a report is queued or generating, **Report history** refreshes its own
  table every few seconds and stops once the report finishes, so the status
  changes from *generating* to *completed* without a browser reload or
  navigating away and back. The operator's search, sort and selection are
  preserved because only the table is repainted.
- Administrators can select archived reports in **Reports → Report history**
  and delete them, individually or with a select-all over the rows currently
  shown. The PDF and metadata are removed together, delivery history cascades,
  and every deletion is audited. A report still queued or generating is
  refused. `reports:delete` is administrator-only; Report Manager keeps
  generation and scheduling but cannot destroy the archive.

### Security

- Chart legends and tooltips render inventory and organisation values as text
  nodes. A business-service name containing HTML can no longer execute script
  in the dashboard.
- PostgreSQL default is now 17 (13 is end-of-life), Grafana default is 13.0.2
  (10.2 is end-of-life), and the UBI Python base image is pinned to a build tag
  instead of `:latest`.
- `scripts/build-release.sh` builds a release archive from a committed tree and
  rejects `.env`, private keys, database data, runtime state and logs. Never
  ship a hand-made ZIP of the working directory again: archives already
  distributed may contain credentials and must be rotated (database password,
  `PATCHTRACK_JWT_SECRET`, `PATCHTRACK_SERVICE_TOKEN`, Grafana admin/DB
  credentials, and any TLS key that was inside the archive).

### Operations

- Every service exposes Prometheus metrics at `/metrics`, with alert rules and
  an optional `monitoring` compose profile (`deploy/monitoring/`).

### System timezone

- **Settings → Platform** now chooses one IANA timezone for the whole
  installation. It sets the local day a daily snapshot covers, the calendar
  boundaries of monthly and quarterly periods, the default zone for new
  schedules, and the timestamps shown in the console and generated PDFs.
- Instants stay stored in UTC; the setting changes interpretation, not
  storage. Existing snapshots and reports are not rewritten.
- The obsolete `PATCHTRACK_APP_TIMEZONE` environment variable has been
  removed; the database setting is authoritative for every service.

### Verification and justification

- A non-compliant, stale or unknown server can now carry a recorded
  verification from Operations or an Administrator: reason, statement,
  remediation plan and target date, plus up to five evidence files (PDF,
  image, text, CSV or Office, 5 MB each).
- Records are versioned. Posting a new verification supersedes the previous
  one and withdrawal retains the history, so the claim that applied when a
  report was produced can still be recovered. Evidence downloads stay behind
  authentication and the `inventory:detail` permission, and every action is
  audited.
- A justification explains a failing state; it does not change the state, the
  dashboard figures or the report numbers.
- Generated reports now contain a **Verified exceptions and remediation**
  section. It lists every failing server in two tables: those with a current
  justification (statement, remediation plan, target, recorder and evidence
  inside the table) and those without one (state, compliance reason and patch
  count). The section is omitted when no server is failing.

### Reports

- Generated PDFs include an **Abbreviations and definitions** page immediately
  after the contents, and the contents lists it. The abbreviation table is
  static; report-specific terms are still defined where they first appear.

### Dashboard

- TV mode now hides the header as well as the navigation, leaving only the
  dashboard on a wall display. Hovering the top edge of the window (or moving
  keyboard focus into it) reveals the header again.

## 3.0.0 — 2026-10-26

First release.

### Capabilities

- **Inventory.** ManagedEngine AssetExplorer connector with a configurable
  field map, immutable `assetexplorer_id`, alias history for renames, and
  reconciliation that refuses to guess when a match is ambiguous.
- **Patch collection.** Red Hat Satellite (host errata), Microsoft
  Configuration Manager (missing updates), and Solaris via an approved
  read-only file drop. No SSH collection anywhere.
- **Local placement overrides.** Operations and administrators can correct a
  server's environment or business service when AssetExplorer is late or wrong.
  The correction is stored beside the source value (`inventory.asset_overrides`),
  the sync keeps running and keeps updating its own columns, and every reader —
  lists, the compliance engine, reports and Grafana — uses the effective value
  through `inventory.asset_effective`. A reason is mandatory, the change is
  audited, the row is marked `LOCAL` with the source value in its tooltip, and
  clearing it returns the AssetExplorer value without a re-sync.
- **Curated placement lists.** Administrators maintain the environment and
  business-service values an operator can choose in **Settings**
  (`inventory.placement_options`): add, rename and delete, with duplicate
  values rejected case-insensitively and the current usage count shown before
  a change. The editor offers the list instead of free text, so a correction
  cannot introduce a second spelling of an existing value. A **rename
  propagates**: the old spelling is recorded in
  `inventory.placement_aliases` and resolved on read by
  `inventory.asset_effective`, so the inventory, filters, dashboard panels,
  compliance engine, reports and Grafana all show the new name while the source
  value is preserved as `*_source` and the next sync cannot restore it. A value
  still in use cannot be deleted — rename it. The AssetExplorer sync never
  writes either table.
- **Integration self-test.** Each integration card and the configuration editor
  can test the source without collecting: endpoint reachability, TLS, credential
  and the first page's shape are checked and reported with a reason and
  duration. A draft can be tested before saving. The probe writes no asset,
  assessment or sync run, so a failed test cannot disturb compliance or the
  integration's health; it is audited as `integration.tested`. For Solaris the
  test verifies the inbox exists, is readable and every waiting document parses.
- **Compliance engine.** Five states (Compliant, Non-compliant, Unknown,
  Stale, Excluded) with a documented numerator and denominator. Unknown and
  stale are counted against compliance. Server percentage and patch counts are
  never blended. Policy is versioned, and every snapshot records the version in
  force.
- **Immutable history.** Daily snapshots with a per-day unique constraint;
  monthly, quarterly and on-demand snapshots; a trend derived from snapshots.
- **Reporting.** Monthly management, quarterly compliance and inventory register
  PDFs, with a generated table of contents, executive summary, breakdowns,
  remediation overview, trend, data-quality statement and methodology.
  Every breakdown, the top-server table and the trend are followed by a
  management statement derived from the same figures, and data quality and
  methodology sit together under **System data integrity**. Validated before publication,
  archived with a SHA-256. Monthly and quarterly schedules with idempotent
  execution. Email delivery tracked separately; a failed send never invalidates
  a report. Reports open with a branded cover — the organisation logo and name,
  title, period and classification — and close with an **Approval and
  sign-off** page carrying separate **Prepared by** and **Concurred by**
  blocks. The organisation name, logo (PNG/JPEG, up to 1 MB, stored in
  `shared.app_settings`) and both signatories are configured in **Settings →
  Report branding**; the logo is verified as an image before it can be
  embedded, and a name-only save preserves it. Report file retention is set at
  **Settings → Retention → Report file retention** and applied immediately — saving
  recalculates the expiry of existing reports and purges already-expired files
  without a restart, while the metadata and SHA-256 remain as a tombstone.
- **Dashboard.** A vanilla-ES-module SPA served by the gateway, plus a
  provisioned Grafana dashboard reading the same tables through a read-only
  role. The application works with Grafana stopped. The executive view offers a
  **Period** control that switches the tiles and breakdowns between the live
  estate and any past month, quarter or year with a recorded snapshot. A
  historical view is built from the latest immutable daily snapshot captured
  inside that period, names the snapshot and the number of daily snapshots it
  rests on, never re-evaluates today's estate under a past label, and refuses a
  dimension filter (a snapshot stores group totals, not server rows). Empty
  periods are not offered. The same view offers a monthly (12 points),
  quarterly (8) or yearly (5) trend basis derived from the
  immutable daily snapshots — each point is the average of the snapshots in
  that calendar period, with the sample count shown — an optional
  auto-refresh (30 s, 1 min, 5 min; pauses while the tab is hidden or a dialog
  is open), and a TV/wall mode that hides the navigation for NOC/SOC displays
  (button, `K`, `Esc`, and the `#/dashboard?tv=1` deep link).
- **Filterable, sortable registers.** Every list — non-compliant servers,
  remediation, the snapshot ledger, server inventory, reconciliation, report
  history, schedules, integrations, compliance policy, users and the audit
  trail — carries a search box, per-field filters and a sort field with a
  direction toggle. Search spans **every column of the row**, flattened,
  rather than a nominated field: one term can match a hostname, an operating
  system, an environment, a business service, a status, an owner, a location or
  a note. Registers held in the page narrow and re-order locally and report
  "showing X of Y rows"; the two paged registers (server list, inventory) pass
  the term and a whitelisted sort key to the API, whose SQL matches the same
  set of columns, so the whole result set is filtered and ordered, not just the
  25 rows on screen.
- **Audit retention.** The retention window is set in **Settings → Retention → Audit trail
  retention** (30–36,500 days, default 2,555) and stored in
  `shared.app_settings`, so a change needs no restart. A daily job deletes
  events older than the cutoff through `shared.purge_audit_events()`; the
  function enforces the range itself and takes no cutoff argument. Everything
  else about the trail remains append-only, and both the setting change and
  each purge are audited.
- **Access control.** Four roles enforced by the backend on every route;
  Argon2id passwords; account lockout; HttpOnly session cookie; CSRF
  double-submit; strict CSP; append-only audit trail with configurable
  retention.

### Deployment

- Docker/Podman Compose on RHEL 9.8 and Rocky 9.8 with SELinux enforcing.
- Native systemd units in `deploy/systemd/` for hosts where containers are
  prohibited: a oneshot migration unit that every service requires, and a
  templated per-service unit with no built-in port so five instances cannot
  collide. The hourly timer is documented in the runbook rather than shipped.
  Validated with `systemd-analyze verify` and pinned by unit tests; never
  started here.
- Single UBI9 python-312 image for all five services, running as UID 1001,
  read-only root filesystem, all capabilities dropped.
- Offline installation from a verified image and wheel bundle.
- No credential, key or default password ships with the product. The first
  administrator is created through a one-time form.

### Fixes found and corrected during development

These were real defects caught by the test suite before release; they are
recorded because each one changed a published figure or a stored record.

- **Freshness rounding slack.** Assessment age was rounded to two decimals
  before being compared with the threshold, so an assessment up to 30 seconds
  over the limit still counted as Compliant. Now compared on the exact
  duration.
- **Phantom IP-change conflicts.** `inet::text` appends `/32`, so every
  unchanged re-sync appeared as an IP change and raised a spurious
  `identifier_changed` conflict. Now compared with `host(ip_address)`.
- **Month-end scheduler drift.** A schedule on the 26th advanced to the 28th
  after its run time passed, and a 31st schedule could not run in February.
  Now clamped to the last day of the target month.
- **Grafana `$__conditionalAll`.** The macro produced invalid SQL for these
  queries. Replaced with an explicit `__all__` sentinel and a plain
  `('$var' = '__all__' OR col = '$var')` predicate.
- **Snapshot dimension constraint.** The original check rejected the dimensions
  the evaluator actually emits, so any snapshot capture failed. Corrected in
  migration 007.
- **Gateway header rendering.** The freshness indicator rendered as
  `[object HTMLSpanElement]` because a DOM node was assigned to `textContent`.
- **A Settings rename did not reach the inventory.** Renaming a placement value
  changed the picker while every server kept the old spelling, and a value
  still in use could be deleted, so the inventory, panels, engine, reports and
  Grafana could disagree with Settings. Renames now propagate through
  `inventory.placement_aliases` resolved at read time (migration 010), deletion
  of an in-use value is refused (409), and migration 011 backfills any value an
  earlier rename left out of the list.
- **Forced password rotation was recorded but never enforced.**
  `must_change_password` was set when an administrator created an account or
  reset a password, but nothing read it, and there was no self-service way for
  a user to change their own password — so the flag could only ever be cleared
  by another administrator reset. The claim is now carried in the access token,
  the gateway refuses every proxied route (403) while it is set, the identity
  service exposes `POST /auth/change-password` (current password required,
  other refresh tokens revoked), and the SPA prompts for the new password at
  first sign-in.
- **A crafted `X-Forwarded-For` broke sign-in.** The application read the raw
  header itself, so any client could put arbitrary text there; the value went
  into an `inet` column and PostgreSQL rejected the whole request — a single
  header was enough to make `/auth/login` return 500. No service parses the
  header now: the address comes from `request.client`, which uvicorn rewrites
  only for peers in `PATCHTRACK_FORWARDED_IPS`, and only a parseable address
  is recorded (NULL otherwise). The backends trust the compose network in
  `PATCHTRACK_INTERNAL_FORWARDED_IPS`, so audit rows still show the operator.
- **Sign out did nothing.** The SPA posted to `/api/session/logout` with a bare
  `fetch`, which carries no `x-patchtrack-csrf` header, so the gateway's CSRF
  middleware answered 403 and the session cookie survived — while the browser
  navigated to the login page as if the sign-out had worked. Now routed through
  the API helper, which supplies the token.
- **The image would not build on its own base image.** Red Hat's UBI python
  image sets `USER 1001`, so every `RUN` before the Dockerfile's final
  `USER 1001` executed unprivileged; the `chmod`/`chown` step failed with
  "Operation not permitted". The build now elevates for that step only.
- **The compose default database image did not exist.**
  `registry.access.redhat.com/ubi9/postgresql-13:latest` returns `NAME_UNKNOWN`
  on an anonymous pull — Red Hat publishes the database images at
  `registry.redhat.io`, behind a subscription and a terms acceptance. The
  default is now `docker.io/library/postgres:13`, which pulls without an
  account; the Red Hat image remains usable through `POSTGRES_IMAGE` and
  `POSTGRES_DATA_DIR`, and the compose file sets both environment-variable
  spellings so either image starts.
- **The one-shot `migrate` service could never run.** Compose overrides `CMD`,
  not `ENTRYPOINT`, and `entrypoint.sh` ignored its arguments — so it demanded
  `PATCHTRACK_SERVICE`, exited 2, and every service that waits on `migrate`
  never started. The entrypoint now executes a supplied command.
- **`PATCHTRACK_LOG_LEVEL=INFO` crash-looped every container.** The documented
  value is capitalised, uvicorn accepts only lowercase level names, and the
  setting was passed straight to `--log-level`. The template now ships
  `info`, and the container entrypoint lowercases whatever it is given.
- **`email-validator` was missing from the image.** The identity service
  models email addresses with pydantic's `EmailStr`, which imports
  `email_validator` at runtime; the package was in the development virtualenv
  but not in `deploy/container/requirements.txt`, so the identity container
  exited on import. Added, and a test now resolves every import in `services/`
  to a declaration in that file.
- **The container applied no migrations at all.** The runner looked for
  `deploy/postgres/migrations` at a fixed depth above its own file — correct
  for `services/common/patchtrack_common` in the checkout, wrong in the image,
  where the package is one level shallower. It found zero files, `migrate`
  exited 0 and printed "nothing (up to date)", and every service then failed on
  its first query with `relation "identity.users" does not exist`. Discovery
  now walks up until it finds the directory, and an absent directory raises
  instead of masquerading as an up-to-date schema.
- **The job runner only knew Docker.** `patchtrack-job.sh` selected the
  container transport with `docker compose`, so on the RHEL/Rocky hosts this
  release targets — where Podman is the shipped runtime — it fell back to the
  native transport and could not reach a port the container deployment does
  not publish. It now detects `docker compose`, `podman-compose`, or `podman
  exec` on the labelled container, pinnable with
  `PATCHTRACK_CONTAINER_CLI=docker|podman`.
- **The gateway proxied to itself.** The four backend URLs default to
  `http://127.0.0.1:800x`, which inside the gateway container is its own
  loopback, so every proxied request failed to connect. Compose now sets them
  to the service names on the project network.
- **The server-list search box did nothing.** The console sent the term as
  `q`; `/compliance/servers` reads `search`. The request succeeded and ignored
  the filter, which is worse than an error: an operator searching for one host
  saw the full list and could believe the host was absent. The parameter was
  corrected and a browser check now asserts that searching narrows the rows and
  that clearing it restores them.
- **Searching a state name also returned the opposite state.** Compliance state
  was matched with `ILIKE '%term%'`, so `Compliant` matched `Non-compliant` as a
  substring and the inventory search for one status showed both. The five
  states are now matched as whole terms (`compliant`, `non_compliant`, …), and
  Server inventory gained an explicit **Status** filter that selects one state
  exactly through the existing `compliance_state` parameter.
- **The search box lost focus and caret on every pause.** Both paged registers
  re-render after a debounced search, which replaced the input mid-word: the
  text cursor disappeared and the operator had to click back in. The box now
  owns the latest text and caret, restores both on the render that replaces it,
  and a response from a superseded request is discarded rather than painted
  over newer typing. The debounce was also lengthened to 500 ms.
- **The business-service panel dropped every group after the seventh.** The
  row chart sliced the response to seven rows without any indication, so an
  eighth service — including a newly configured or locally corrected one —
  was absent from the dashboard. Every group is now drawn, and a long list
  scrolls inside the panel.
- **The operating-system panel grouped by version.** It showed `9.4`, `2022`
  and `11.4` instead of the platform, so RHEL, Windows and Solaris could not
  be compared. `/summary` now groups by `os_family`, and the panel labels the
  families RHEL, Microsoft Windows, Solaris and Other. The environment panel
  was checked at the same time and does move a server between groups when its
  environment override changes.

### Known limitations

- No MFA and no OIDC/enterprise sign-in (the schema accommodates the latter;
  the login path refuses such accounts with an explanatory message).
- Role model is global: a Viewer sees the whole estate.
- Scheduled work runs in-app; cron and external timers are deliberately not
  supported. (An earlier release used a systemd timer; see the Unreleased
  section for the upgrade step.)
- Business-level Prometheus gauges (collection age, stuck reports) are not
  exported yet; only HTTP, uptime and scrape health are. See
  `deploy/monitoring/README.md`.
- The four systemd units in `deploy/systemd/` are written but have never been
  started: this host has no `patchtrack` account, no `/etc/patchtrack` and no
  system postgresql-13 service. They are validated with
  `systemd-analyze verify` only. See
  [operations-runbook.md](operations-runbook.md#5-running-natively-under-systemd).
- The Grafana read-only role was created and exercised on the build host —
  `SELECT` succeeds on the dashboard tables while `INSERT`, `DELETE` and any
  access to `identity` are refused — but the target still needs
  `deploy/postgres/roles/010_grafana_readonly.sql` run against its own
  database, because the password is generated per deployment and is not
  shipped.
